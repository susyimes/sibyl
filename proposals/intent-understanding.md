# Sibyl 理解层

已并入[理解模块 v1](../understand/SPEC.md) · 2026-11-18

用户输入 `/sibyl <想做的事>`，当前 Agent 结合这段对话和手头的项目，写出三条可以直接交给它做的提示词。用户读到的是三个具体成品的样子，回 `s1`、`s2` 或 `s3` 就能选。理解层放在任务入口，负责把「做什么」说具体。选定后，宿主照常负责规划或执行。

## 一次对话

假设前文已经确定，项目是低多边形港口，主要在手机竖屏上看，已有拖动镜头。用户发来一句 `/sibyl 做个 threejs 船`。

> **Sibyl 理解**
>
> 沿用现有的低多边形港口、手机竖屏和拖动镜头。
>
> **s1. 港口里的拖轮**　请用 Three.js 给现有的手机竖屏低多边形港口做一艘靠泊拖轮。让它矮宽、吃水深，白色驾驶舱略向前倾，两舷各挂几只旧轮胎作护舷。船身、甲板和驾驶舱要有清楚的层次，即使在手机上缩小也能一眼认出船头。把它放在码头边，留出水面和栈桥作尺度参照。沿用现有拖动镜头，拖到另一侧仍能看清整艘船，也能看见船舷与码头之间的空隙。
>
> **s2. 一段渔船归港的小景**　请在现有的手机竖屏低多边形港口里，用 Three.js 加一艘清晨归港的渔船。船身刷成褪色的蓝绿，船头垫一圈旧轮胎，船尾收着一叠渔网。打开场景时，它从防波堤外缓缓转入，船尾留下一道渐散的水纹，接近栈桥时减速，停稳后随水轻晃。请复用已有的拖动镜头，让我在进港途中也能换角度观察。验收时要能在竖屏里看完从入港到靠岸的全过程，船舷和栈桥始终留有清楚的间距。
>
> **s3. 指哪开哪的小渡船**　请用 Three.js 给现有的手机竖屏低多边形港口加一艘小渡船，让我单手就能指挥它往返。在港内放两个看得清的停靠点，给船做一道醒目的舷边色带，远一点也能跟住它。轻点另一处码头，船就逐渐转向、驶近并减速停稳，拖动屏幕仍然操作已有镜头。请把点选和拖动区分开。验收时我能连续指挥它往返一趟，途中拖动看清侧面，再松手也不会误发新的航行指令。

用户回 `s2，改成黄昏，不要尾流`，Agent 就按已有港口里的黄昏归港场景开工，保留进港、靠岸和轻晃，去掉尾流。如果回复是 `s2，只给我最终提示词`，这一轮就交付可复制的提示词。原请求是「先设计」或宿主处于 Plan 模式时，选择后进入设计或规划。

同一句话，若前文是「我要一批能放进关卡编辑器的静态船模」，三条就应该变成同一套尺度、原点和美术风格下的模型方向，例如靠剪影辨认的拖轮、靠甲板索具辨认的渔船、靠双层客舱辨认的渡轮。此时加一段进港动画会偏离任务。这里的尺度、原点若尚未约定，就沿用项目里可查到的资产约定，或写成候选建议。

## Agent 怎么展开一句话

1. **先找出已经决定的部分。** 读用户原话和本轮补充，带上对话中仍然有效的用途、交付物和限制。涉及已有作品时就近核对相应文件。用户提到「沿用上次那艘船」时，可以按项目回查理解历史里选定的那次委托。用作共同条件的每一项都应该有出处。
2. **找一个值得用户选的分歧。** 想清楚「用户选了另一条，最后拿到手的东西会有什么可见差别？」示例里的分歧是看船本身、看一段演出、亲手操控。若「操控一艘船」已经确定，分歧就可以换成操控手感或具体玩法。`s1` 放最贴原话和已有工作的版本，`s2`、`s3` 各沿有依据的方向多想一步。
3. **把用户原话改写成三份完整输入。** 每条用一到两段写清要交付什么、已有约束、关键细节和验收方式，使用户可以将其中任何一条单独复制到新对话。短创作请求通常可展开为每条约 150–3000 个中文字，题意简单时按需缩短。船型、时间、动作之类的新主意放在相应候选里。选项按贴合度排列，省去预测概率。
4. **把可合理补全的细节直接端出来。** 普通歧义用三条候选让用户选。只有缺少指代对象或存在影响所有候选的硬冲突，才先问一个能解开它的问题。例如「照刚才第二张图做」而当前会话看不到那张图，可以先请用户补图。单说「做艘船」已经足够给出第一组。

## 输入和选择

| 当前输入 | 理解层的行为 |
|---|---|
| `/sibyl <请求>` | 在当前会话生成一组候选并等待。新请求取代上一组。空命令只提示用户补一句想做的事。 |
| `s2` 或 `S2，<补充>` | 取本会话最近一组实际展示的第 2 条。将原请求、可见的共同条件、所选提示词及补充交回当前 Agent。后写的明确修改覆盖对应旧细节。 |
| `换一组，<偏好>` | 在等待选择时，保留原请求和已确认条件，带着补充重新生成三条。新一组展示后使用新的编号对应关系。 |
| `取消` | 结束本次理解，回到普通会话。 |
| 纯数字或另一条普通请求 | 按宿主原有含义处理，结束本次待选。有效的选择必须引用当前展示的选项。 |

选中的内容以用户看见的文字为准。接入层把这些文字随原始 `s2` 消息作为上下文交给 Agent。等待选择时仅做理解所需的只读检查。即使 `/predict on act` 已开，显示候选后也等待用户。执行阶段沿用当前宿主模式和权限。

## 理解和推测各自存什么

两层共用当前对话，各有自己的待选状态、历史和读取入口。首版沿用现有本地文件布局，给理解层单开目录。路径确定归属，记录的 `layer` 字段让两类数据在导出或汇总后仍能分辨。

| | 推测层 `predict` | 理解层 `understand` |
|---|---|---|
| 待选状态 | `~/.sibyl/sessions/<id>.json` 中已有的 `last` 等字段 | `~/.sibyl/understand/sessions/<id>.json`，保存当前实际展示的候选和来源消息 |
| 历史 | `~/.sibyl/journal.jsonl`，记录猜了哪些下一句、各自概率、用户实际回了什么 | `~/.sibyl/understand/journal.jsonl`，每次选定留一条委托，保留当时的候选、用户选项和修订 |
| 读取和学习 | `/predict stats`、`/predict learn` 和现有 `LEARNED.md` 继续使用推测数据 | 按项目和任务回查当时选定的委托。首版只保存有出处的记录，长期偏好学习留待以后设计 |

理解记录显式写 `layer: "understand"`。读取已有推测文件时，由推测读取器给旧记录标出 `layer: "predict"`。这样老版本可以继续写原格式。`/predict forget` 按原范围清理推测资料，理解历史可独立清理。

一条理解记录需要足够回答「这句话是谁加的，用户最后选了什么」。以归港的例子为准：

| 字段 | 记录的内容 |
|---|---|
| `request`、`context` | 用户原话「做个 threejs 船」，以及展示给用户的共同条件。共同条件注明来自哪条会话消息或哪个项目文件。 |
| `choices` | 当时展示的三条提示词原文。「清晨」和「尾流」的来源都是 Agent 提议。 |
| `selection` | 选中的 `s2`，以及用户逐字写下的「改成黄昏，不要尾流」。 |
| `effectiveRequest` | 实际交给宿主的委托，保留选择与修订的优先级。已确认的范围是这一次黄昏归港。 |

每条记录带项目、会话、轮次和选择消息的标识，方便回查和去重。待选时三条都只是提议。取消或换组会释放被替代的候选，只有用户选定才追加历史。未选项在已选记录中仅用于还原当时的选择。`journal: false` 同样关闭理解历史的落盘，完成本次选择只使用会话中的临时数据。

## 接进现有仓库

首版做成可选的 `understand/` 模块。安装时登记一个能把参数传给当前会话的 `/sibyl` 入口。有原生命令就用原生命令，宿主能把普通消息直接交给 Agent 时也可以识别消息开头的 `/sibyl`。两种方式都要在原任务开始前拿到请求。只在轮末读取会话记录的能力，足以统计回复，来不及拦住已经开始的实现。[基础规范的模块约定](../SPEC.md#11-optional-modules)

| 接入位置 | 首版行为 |
|---|---|
| 用户输入时 | 在进化模块的 `recordReply` 前识别 `/sibyl` 和待选回复。进入理解时使上一组预测及其临时上下文失效。理解交互只走理解层的记录入口。选择后保留宿主收到的真实用户消息，并把所选委托交给同一个 Agent。 |
| 展示候选时 | 用独立标题 `Sibyl 理解`。在生成、换组和取消这些轮次，接入层凭本轮类型直接放行结束，跳过基础 `decide` 和进化模块的 `rememberPrediction`。仅换标题仍会触发自动续轮。选定后实际处理任务的轮次恢复正常的轮末预测。 |
| 跨轮选择时 | 使用理解层自己的会话状态和宿主消息 ID，候选完整展示后才允许选择。选择指向这一组的标识，重复投递同一条回复也只派发一次。新请求、取消和选定会使旧组失效。状态丢失而无法从该会话核对原文时，请用户重新展开。 |
| 开关与安装 | `/predict off` 管自动预测。用户显式输入 `/sibyl` 可做一次理解，随后维持原开关。普通关闭轮次保持原有快路。沿用 `SIBYL=off` 的强制关闭和基础安装的 `disable`、`uninstall` 生命周期。 |

模块说明负责指导同一个 Agent 阅读上下文和生成候选。参考核心以纯函数识别输入、解析选择、组装交给宿主的委托，并返回应写的状态和记录。接入层负责按 `layer` 向对应的文件写入。

## 实现顺序和验收

1. 在 `understand/SPEC.md` 固定命令、候选格式、回合边界及生成说明。用两段不同前文配同一句船的请求，人工评审是否继承约束、三条是否真的改变成品、能否直接开工。
2. 补参考核心和 `understand/cases.jsonl`。覆盖选择加修订、换组、取消、纯数字、不同会话、重复消息，以及旧组失效。专测一个相同编号的例子：旧推测 `s2` 是「跑测试」，新理解 `s2` 是「渔船归港」。人选 `s2` 后只新增一条理解历史，推测样本数和命中率都维持原值。另测 `journal: false`、读取无标签的旧推测记录和两层各自清理。运行原有两套 `--repo` 一致性检查。
3. 先在已有 Sibyl 接入经验的 Grok CLI 做真会话验收。重点看 `/sibyl` 的参数是否在开工前到达当前 Agent，`act` 下是否只出现一组菜单，选后是否只执行一次，以及 `/predict off` 时的一次性调用和预测日志是否符合预期。通过后再将模块列入正式安装说明。
