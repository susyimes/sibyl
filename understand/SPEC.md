# Sibyl understanding module v1

> Add the Sibyl understanding module to your existing Sibyl installation according to this file. Install it yourself for your current agent and verify it in real conversations.

The explicit command is `/sibyl <request>`. It runs once in the current conversation. The agent actively elaborates the request into three different usable prompts. The person can choose one, amend it, request another set, or cancel. `/predict` still controls turn-end prediction. This module needs the installed base, and works with or without the evolution module.

## User interaction

Use the same agent, conversation and current project to do the reasoning. Use `OFFER_BRIEF` from [the reference core](understand_core.mjs) for the generation turn. Consider earlier constraints and user instructions before inventing new details. Use only read-only inspection when necessary to frame a choice. Each choice is written as a commission with an observable outcome. The first is the closest fit. Each other choice resolves an open decision in a materially different way. Do not create the requested artifact before the person chooses. This also applies when prediction is in `act` mode.

The product is three optimized versions of the user's **input**. Each can be pasted into a fresh chat on its own. Include the goal, relevant context, concrete details and a recognizable completion condition in the option itself. A terse creative or technical request will generally benefit from about 150–300 Chinese characters per candidate; density and faithfulness matter more than length. Let the alternatives clarify the same intent with different emphases. Carry an existing project convention forward using the available evidence. For example, if the project specifies a common scale and origin without numbers, preserve that requirement in every rewrite.

The first line is `Sibyl 理解` (also accepted: `Sibyl Understand`). A short paragraph of visible shared context may follow, with a conversational or project source. Give exactly three labelled prompts `s1.`, `s2.` and `s3.` in order, no probabilities or footer. A prompt may span two paragraphs. Preserve its paragraphs through selection and storage. The user must see the full text they are selecting. If a missing referent or a hard contradiction blocks every useful interpretation, give the heading and one line starting with `?` and the essential question. The reply is a refinement of the original request.

| Input | Result |
|---|---|
| `/sibyl 做个 Three.js 船` | Replace any previous menu, show the new choices and wait. |
| `/sibyl` | Show a short usage example. |
| `s2` or `S2，改成黄昏，不要尾流` | Use the exact second choice from this session, with the latest user amendment taking precedence. |
| `换一组，更写实` or `regenerate, more realistic` | Generate another set from the original request and accumulated user refinements. |
| `取消` or `cancel` | Release the pending menu. |
| A bare number, other ordinary request or other slash command | Release the menu and leave the input to its normal handler. With no menu, `s2` retains its usual host/prediction meaning. |

The selected task respects the user's current instructions and host mode. A prompt-only pick returns a usable prompt, a plan-only pick yields a plan, and an implementation pick starts work. A single task choice is evidence about that task.

## Input and turn-end integration

Find an explicit command path **before the agent starts the requested work**, plus the session id, user input, and delivered assistant message. Register `/sibyl` as a user-invocable command or skill where supported. Some hosts reject unknown slash commands before calling submit hooks, so a submit hook alone may not register the command. Prefer explicit-only invocation. Preserve the raw arguments and register the name once. If the name already belongs to another installation, preserve it and report the conflict.

1. On real user input, process understanding before prediction reply logging or ordinary task execution. `UnderstandingStore.submit({session, project, messageId, prompt, journal})` returns an `action`, an updated understanding `state`, and if applicable a `reason` and `record`. Supply a stable host message ID, or derive one from the session and this input's stable transcript position. Repeated text in **different** messages is legitimate. Ignore subagent, tool and teardown events.
2. On `offer`, send `reason` to the same agent in this turn and remember its `state.roundId`. A host-native skill may expand the actual command arguments with `OFFER_BRIEF`. On `notice`, show `reason` and end this interaction. On `duplicate` avoid double dispatch. On `pass`, use the ordinary path. On entry into understanding, retire any pending prediction (`last`, `answer` if evolution is installed) in its owning session. Skip `recordReply` for each input owned by understanding, including the selection.
3. On the genuine end of the offer turn, call `store.finish({session, roundId, finalText})` **before** base `decide` and `rememberPrediction`. Use the turn's own round ID. For `ready` or `question`, end immediately. Duplicate Stop events for the same offer end quietly. An incomplete or malformed reply never installs a selectable menu. The host may request one formatting retry in the same turn or tell the user to regenerate. Ignore stale completions. No second prediction menu and no automatic choice, even in `act`.
4. On `select`, the returned `reason` is the selected commission with its provenance and amendments. Deliver it alongside the authentic user message, under ordinary user authority. A host that cannot attach context to an accepted submit may use the exact delivered menu and the selection instructions already in the conversation. Verify this in a real resumed turn. If the menu is unavailable after compaction, recover the recorded visible text through the host or ask to regenerate. Never execute a guessed binding. After the selection, the task's genuine end can again run the normal prediction flow. On refresh and clarification follow-ups the previous skill instructions can similarly guide a host that preserves conversation context.
5. An explicit `/sibyl` works once with `/predict off` and does not turn prediction on. A host-wide `SIBYL=off` or disabled installation takes precedence. Include the native command in disable/re-enable/uninstall handling. A native skill must respect global opt-out on its own dispatch path as well. Interrupted/failed turns must not make a partial menu selectable. Storage failure while resolving a selection should explain that the user can resubmit the full visible prompt.

## Separate state and storage

Use an understanding-owned directory. Locally this is `~/.sibyl/understand/`. `sessions/<id>.json` holds the current menu and recent delivery IDs. `journal.jsonl` contains one selected commission per line. Drafting, refreshing, cancelling, and ordinary messages add zero history entries. Forecasts remain in the existing prediction journal and its statistics. When exporting mixed data, old entries from the **prediction journal** have `layer: "predict"`. Understanding records always have `layer: "understand"`.

A selection record contains `at`, `session`, `project`, `roundId`, `messageId`, `request`, `refinements`, visible `context`, the three displayed `choices`, `selection` with its `label`, verbatim user `reply` and `extra`, and `effectiveRequest`. Never treat an unselected idea or a superseded detail as an instruction. Honour `journal: false` in the effective `PREDICT.md`, even without evolution installed. Only temporary interaction state and opaque deduplication IDs are needed in that case. The prediction statistics, learning and forget commands operate exclusively on prediction data.

[understand_core.mjs](understand_core.mjs) contains pure functions. [file_store.mjs](file_store.mjs) is a dependency-free Node adapter providing `new UnderstandingStore(directory)`, `.current(session)`, `.submit(event)` and `.finish(event)`. It handles concurrent callers, writes through temporary files and recovers an interrupted journal write. Scope file I/O to this directory. Put this agent's **code** with its installation files, away from the shared data even if the base is in the earlier flat layout. Other languages may port the functions and storage contract.

## Self-installation and acceptance

Inspect the existing base and its install record, find the input and final-message capabilities, and keep every pre-existing registration and user setting. Copy the reference module (or port it), add the integration and native `/sibyl`, and record owned changes and backups in this agent's installation record. When experimenting with an existing online installation and a local source checkout, copy this module from the requested checkout. Run `node understand/run.mjs` in the repository or `node run.mjs` from a copied module. Run the base and, when installed, evolution conformance as well.

Check `/predict status` through the same ordinary slash-command input. An existing hook-only base installed on an earlier host version may need its `/predict` name registered with the host's command dispatcher for its original handler to receive user input. Keep the original handler and include any restored registration in the installation record.

Then use the **installed agent binary and actual user input**. Check that a genuine `/sibyl` appears in the host and resolves in a fresh session. Give it context about a mobile low-poly harbor, then `/sibyl 做个 Three.js 船`. Observe a single three-choice menu and no work on the boat. Reply `s2，改成黄昏，不要尾流，只给我最终提示词` in the same session. Verify the concrete selected prompt, one understanding record and no prediction journal entry for that choice. Also check regeneration or cancellation, `act` interaction and explicit use with predictions off. Test with a different project or prior constraint, such as static assets only, to check that the proposed alternatives change. Check lifecycle or destructive paths against an isolated copy. A parser test or a direct hook invocation does not by itself establish that a native command works.
